# API reference

Base URL (local): `http://localhost:8000`. Interactive Swagger docs: `http://localhost:8000/docs` (generated by FastAPI from the Pydantic models in `backend/app/schemas/api.py`).

The examples below are **real responses** captured from a running instance (Docker stack, and a local run for the analytics example) in offline-mock mode on 2026-10-14 (long arrays shortened with `…`). With a Claude key configured, `provider`/`model` change, `usage` contains token counts and a cost estimate, and `answer` is written by the model from the returned rows.

Every response carries an `X-Request-ID` header. Send your own (a UUID) to correlate logs.

`X-Client-ID` (optional, 16–64 characters `[A-Za-z0-9-]`): an anonymous per-browser ID. The frontend sends one automatically. With `HISTORY_SCOPE=client`, `/api/history` only returns requests made with the same ID; the server stores only its SHA-256 hash.

## Errors

Request problems use one envelope and an HTTP status:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "The request body is invalid.",
    "request_id": "58d1abce-0b55-45ad-9d18-0156dbaa8a93",
    "details": {
      "fields": [{ "field": "question", "message": "String should have at least 3 characters" }]
    }
  }
}
```

| HTTP | `code` | When |
|---|---|---|
| 400 | `question_too_long` | Over `MAX_QUESTION_LENGTH` |
| 404 | `not_found` / `http_error` | Unknown history ID / unknown route |
| 422 | `invalid_request` | Body fails Pydantic validation |
| 429 | `rate_limited` | Over `RATE_LIMIT_PER_MINUTE`; `details.retry_after_seconds` |
| 429 | `daily_limit_reached` | Daily LLM request or estimated-cost cap reached for all visitors (cache hits still work) |
| 429 | `usage_unavailable` | Caps are configured but today's usage can't be read; fails closed |
| 500 | `internal_error` | Unexpected bug. Generic message; the traceback only goes to the server log |

Stack traces, file paths and API keys never appear in responses.

## GET /api/health

```json
{
  "status": "ok",
  "version": "1.0.0",
  "database": "ok",
  "database_detail": null,
  "schema_version": "a8fc4bcf139097e5",
  "llm_provider": "mock",
  "llm_configured": false,
  "history_storage": "persistent",
  "uptime_seconds": 27.6
}
```

`status` is `degraded` (still HTTP 200) when the business database can't be reached, or when history fell back to temporary in-memory storage because its database is unreachable (`history_storage: "temporary"`).

## POST /api/query

Request:

```json
{ "question": "Show the top five products by revenue.", "use_cache": true }
```

`question`: 3–500 characters. `use_cache: false` forces a fresh run.

Response (success):

```json
{
  "request_id": "…",
  "created_at": "2026-10-14T15:38:…Z",
  "question": "Show the top five products by revenue.",
  "status": "success",
  "answer": "The query returned 5 rows. First row - product id: 8, name: Halo Noise-Cancelling Headphones, revenue: 47,934.37.",

      "llm_latency_ms": 0.48, "db_latency_ms": 4.83 }
```

Field notes:

- `sql` is the **canonical** SQL re-rendered by the validator — exactly what ran. `attempts[].sql` is what the model wrote.
- `columns[].type` is inferred from the values: `number`, `date`, `string`, `boolean`, or `null`.
- `truncated: true` means the result hit `max_rows`; only the first `max_rows` rows are returned.
- `warnings` lists things to know about a *successful* result: the row limit was hit, or the question asked for N items and the final attempt still returned more.
- `usage.cost_status`: `estimated` (tokens × configured price), `unavailable` (tokens or price unknown — never shown as $0), or `no_llm_calls` (cache hit, genuinely $0).

```json
  "…": "…"
```

Other `status` values and their `error.code`:

| status | error.code examples | Retried? |
|---|---|---|
| `rejected` | `forbidden_statement`, `multiple_statements`, `table_not_allowed`, `forbidden_function`, `operation_not_permitted` | Never |
| `failed` | `retries_exhausted`, `query_timeout`, `llm_provider_error` | Exhausted / no |
| `unanswerable` | `unanswerable` | No |

Attempt `status` values: `success`, `validation_error`, `execution_error`, `result_check_failed`, `security_violation`, `parse_error`, `unanswerable`, `timeout`, `provider_error`.

Recoverable `error_code`s an attempt can carry (each triggers a correction): `sql_syntax_error`, `unknown_table`, `unknown_column`, `unknown_value` (a string compared with a categorical column isn't one of its real values), `business_rule_violation` (revenue computed without the order-status rule), `sql_runtime_error`, `row_count_mismatch` (more rows than the question asked for), `llm_response_invalid`.

## GET /api/history/{request_id}

Everything in a history item, plus `error_message`, `error_category`, `explanation`, `answer`, `attempts`, `tables_used`, `assumptions`, `llm_calls`, `provider`, `model`, `input_tokens`, `output_tokens`, `generation_ms`, `db_ms`. Result rows are not stored.
